# 场景关系证据模型

## 两层关系

本 Skill 严格区分两层：

1. **底层数据证据**：字段指纹重合、文件哈希、显式文件引用、表头结构和带定位的文档句子。
2. **场景语义关系**：参与方、输入、活动、对象、规则、决策、状态、系统和输出之间的业务关系。

底层证据不是最终图。具体值只用于证明“这两份材料可关联”，不能成为节点，也不能自动推出时间顺序或因果关系。

## 证据卡

每张卡包含稳定 `E-...` ID、类型、强度、说明、来源文件、定位和有界事实。

| 类型 | 含义 | 可证明范围 |
|---|---|---|
| `scenario_goal` | 用户提供的业务目标 | 词汇和范围，不能独立证明关系 |
| `goal_relation_statement` | 场景描述中明确的要求、条件或结果 | 用户明确规定的业务关系 |
| `file_structure` | 文件类型、大小、表数量和解析状态 | 材料存在及覆盖 |
| `table_schema` | 表头按业务角色分组 | 材料角色和概念存在 |
| `table_process_signal` | 同一表中多种业务角色共现 | 结构联系，不能独立确定时序 |
| `field_relationship` | 不暴露原值的精确指纹联系 | 跨材料追溯、引用或依赖 |
| `record_trace` | 同一结果锚点沿已发现键组命中的有界脱敏行包 | 证明一个真实业务实例可贯通来源；不自动定义全部规则或标准流程 |
| `table_relation_statement` | 小型高信号表中带单元格定位的规则或条件短句 | 短句明确表达的约束、条件或结果 |
| `document_relation_statement` | 带页码/段落/OCR 行号的关系句 | 句子明确表达的方向、条件或结果 |
| `material_topic_alignment` | 文本主题与另一份材料文件名语义对齐 | 主题相关性，只能作为补强证据 |
| `document_outline` | 有界标题与大纲 | 文档角色和上下文 |

关系证据规则：

- `references`、`depends_on`、`joins_with` 可以由精确 `field_relationship` 直接支撑。
- `feeds` 可由精确跨材料关系与材料角色共同支撑；`governs`、`derives` 优先要求场景描述或明确关系句。
- `triggers`、`precedes`、`branches_to`、`returns_to` 优先要求明确的场景、表格或文档关系句；没有直接关系句时，至少需要流程结构卡与另一张独立结构/直接证据共同支撑。
- `produces`、`consumes`、`transforms`、`updates`、`governed_by`、`performed_by` 需要明确关系句，或多张相互支持的结构/直接证据。
- 场景目标和文件元数据不能独立证明一条业务边。

## 场景图约束

- 节点类型：`trigger`、`actor`、`input`、`activity`、`object`、`rule`、`decision`、`state`、`system`、`output`。
- 边类型另含宏观数据关系 `feeds`、`joins_with`、`governs`、`derives`；优先用这些类型形成数据底图。
- `main_chain` 是兼容字段，语义为主数据路径；至少三个节点，起点为触发、输入、参与方或系统，终点为输出、状态或对象。
- 主数据路径相邻节点间必须有同方向的数据流或推导边。
- 最终图最多 10 个节点、14 条边、3 个分支；建议保持在 5-8 个节点。
- 分支首边必须是 `branches_to`，并从已经挂接的节点出发。
- 所有节点在无向视角下必须属于同一连通分量。
- 图中每个纳入文件必须出现在节点、关系或分支引用的证据来源中。

## 覆盖与不确定性

`complete` 表示：

- 底层探针完成所有可解析表的候选列扫描；
- 文档按声明的字符预算提取了关系证据；
- 文件均被纳入图或有证据地排除；
- 最终图通过连通性、主支链和证据门槛验证。

它不表示系统能够证明原始材料中没有任何未明说的隐含关系。不能达到门槛的猜想不进入最终边，应在报告中列为待业务确认项。

## 大数据性能边界

- 从规则表、结果样例和其他小型高信息密度材料开始，把高特异性业务键转成不可逆指纹，再只定向扫描大表候选列。因此结果样例中的一条真实链路可以探测千万行来源，而无需把千万行送入 Agent。
- XLSX 表头目录探测直接流式读取 OOXML 前 64 个物理行，不加载整张工作表，也不依赖表头位于第一行；大表值探测使用 `fastexcel + pyarrow` 列式匹配，只把命中行和有界样本物化给 Python。
- `openpyxl` 只用于小表或异常文件后备。大型 XLSX 缺少 `fastexcel + pyarrow` 时必须明确报告依赖降级，不允许悄悄进入无界慢扫描。
- CSV/TSV、JSONL、SQLite 流式读取；Parquet 用列式读取。
- 不持久化全量 distinct 值，不拼接大表整行，不为每个单元格执行实体正则。
- 结果锚定追踪对大表执行全量列式/流式搜索，但每个来源只物化有限行、有限列；每条键值仅保存脱敏展示与不可逆指纹，禁止把全量命中送入 Agent。
- 种子、bottom-k 列摘要、每值命中数、文档字符数、每文件关系句和总证据卡数均有上限。
- 列式扫描按表写断点；流式后备每 100,000 行写断点。检查点使用紧凑 JSON，`partial` 后用原命令恢复。
- OCR 原文只存在临时文件，进入 Agent 上下文的只有短证据卡。

## 数据执行契约门禁

宏观关系图通过后仍必须生成 `operational-data-contract.json`。它把“图上可关联”收敛为第三方运行时可验证的执行假设：

- Excel/CSV 先从前 64 个物理行自动识别真实表头；评分同时考虑行宽、后续数据行稳定性、文本/数值差异和字段语义，不依赖某个业务领域的固定列名。表头置信度不足或通用列名占比过高时阻塞。
- 每个来源都记录生命周期：`runtime_input` 是当前业务批次可能提供的输入；`design_time_template` 是历史结果或格式样例；`design_time_evidence` 只支撑蒸馏。生命周期不因文件是表格、PDF、图片、Word、TXT 或 Markdown 而改变。
- 每个结构化来源记录相对路径、表/工作表、列、规模和业务角色；大来源只能走只读 SQL。结果样例只保留输出结构、类型、定位和可选的有界脱敏示例，原文件在第三方运行时可以不存在。
- 同名字段不是连接结论。候选按精确证据、ID/编码语义、结果反向追踪和基数特征排序，同时保留单键和有证据字段组成的复合键候选；运行时必须逐键组校验双向未匹配、唯一性、基数与连接放大。
- `trace_evidence` 必须引用 fingerprint 匹配的 `trace-samples.json`。存在结构化结果样例时，至少一个结果锚点必须沿精确键命中业务来源；规则可通过带行号的局部语义证据附着。无法形成同锚点链路时阻塞，而不是回退随机样本。
- 每个来源记录的内容摘要是设计期证据指纹，不是新一批运行数据的身份约束。第三方运行时按 `source_id` 显式绑定实际文件，校验文件仍位于数据根目录且字段/章节契约兼容；不得要求大小或内容摘要与历史样本相同。
- PDF、图片、TXT、Markdown、Word 等记录解析/OCR、分块索引、定位和摘要要求；语义检索路径只找证据，不能代替主键连接。
- 外部知识库、爬虫、Web 检索和远程 API 是 `optional_enrichment` 能力，不是本地文件来源。Agent 根据用户目标和完整规则决定是否调用；当某项外部知识对判断必不可少且所有提供方都不可用或无结果时，状态必须为 `manual_intervention_required`，禁止猜测。
- 多个核心输入源不能形成完整执行网络，规则节点没有来源，或结果样例无法反向追踪时，契约为 `blocked`。后续流程和 Skill 蒸馏必须停止。

`ready` 不是“绝对没有错误”的承诺；它表示所有可自动验证的链路门禁已通过，剩余不确定性以 warnings 和运行时校验显式保留。
