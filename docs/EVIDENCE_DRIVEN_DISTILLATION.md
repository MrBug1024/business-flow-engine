# 证据驱动的业务蒸馏与发布方法

## 核心原则

业务能力包不是把历史结果、字段名或几段提示词拼在一起。它是对一条可复核的业务计算链的可移植实现：运行时输入如何被定位、按什么键组合、受哪一条完整规则约束、经过哪些筛选、计算、去重、聚合和输出映射，最终怎样得到可比对的结果。

因此，数据链路、业务流程和能力包分别回答不同的问题：

| 层级 | 必须证明的事实 | 不能单独证明的事实 |
| --- | --- | --- |
| 数据链路 | 某个历史结果记录能精确定位到哪些来源记录、表粒度、键组和基数 | 筛选、计算或规则为什么会得到该结果 |
| 微观复现 | 来源记录经已声明的算子能够重建结果字段和集合 | 该算子适用于所有未来批次 |
| 宏观流程 | 稳定的责任、输入输出、规则、分支和异常如何协同 | 具体规则实现已经可执行 |
| 能力包 | 已批准的算子和规则配方可在新数据上执行并给出血缘 | 未经历史回放验证的业务结论 |

任何一层缺失都必须停止在该层，不能用模型猜测补齐，更不能把包标为“已发布”。

## 平台状态机

每个业务场景都有独立的版本化蒸馏运行，不与聊天轮次绑定。输入文件、角色、表结构或用户纠偏变更时，运行版本递增，所有下游产物和审批自动失效。

```mermaid
flowchart LR
  S[场景与范围确认] --> R[文件/表/字段角色确认]
  R --> A[结果锚点选择]
  A --> T[结果锚定链路追踪]
  T --> V[逐边审阅与纠偏]
  V --> M[微观复现契约]
  M --> F[宏观业务流程]
  F --> C[规则/算子配方编译]
  C --> H[历史回放与留出批次验收]
  H --> P[发布与第三方 Agent 黑盒验证]
```

AI 在每个阶段只能生成候选、解释证据和提出问题。角色确认、锚点选择、链路批准、微观算子批准和发布批准都必须由当前登录用户通过平台接口写入，并且绑定当前产物哈希与运行版本。

## 数据链路的正确单位

关系端点不是“文件 + 同名字段”，而是：

```text
数据集版本（内容指纹）
  -> 表身份（文件、sheet/table、表头范围、schema 指纹）
  -> 业务粒度与已批准键组
  -> 记录集合 / 结果锚点
  -> 处理算子
  -> 结果字段
```

每个结果锚点必须由用户选择的结果表、批次/状态/业务键选择器确定。系统可提供脱敏候选和覆盖统计，但不能把物理第一行、随机行或来自不同批次的行拼成一条链。一个链路样本中可以有 `R -> A[n]、B[x]、C[y]`，也可以有一对多明细集合；所有关系必须保留表身份、已批准键组、空值率、未匹配率、重复率、扇出及截断边界。

## 不确定性如何处理

不确定性不是一段聊天文本，而是一个阻断条件和可操作问题：

- 结果表、来源表或表粒度不确定：要求用户确认角色，不能开始追踪。
- 多个候选键或疑似复合键：展示每个候选的命中、未匹配、扇出和反例；用户选择或修正键组后重新追踪。
- 一对多或多对多：用户必须声明其业务含义，以及是否逐明细、聚合、去重或拒绝；“接受警示”不是批准。
- 规则记录不唯一：要求用完整规则定位条件选择，不能以规则类型或关键词把多条规则混为一条。
- 输出字段没有可复现算子：记录为关键未解问题，阻断流程、蒸馏和发布。

纠偏只描述结构（表、字段、键组、基数、算子类别和业务理由），不把历史行号或单元格值写成未来规则。

## 微观复现与回放

链路批准后，平台将每个已确认锚点写成独立的复现用例。微观复现必须显式声明并由用户确认：

1. 规则如何选择完整记录；
2. 关联使用哪一组键以及基数处理；
3. 筛选、计算、去重、聚合、排序和输出映射；
4. 哪些字段是运行时参数，哪些来自规则记录；
5. 结果字段/集合/统计应如何与历史结果比较。

历史结果在此阶段只充当 oracle：包运行时只绑定新的业务输入和规则输入，回放器将执行结果与历史锚点逐字段、逐集合和逐基数比对。至少应保留一个未参与编译的结果锚点或批次作为留出验证；只有单一历史样本时，平台必须明确降级为“单例验证”，不得声称泛化可靠。

## 发布门禁

可配置给第三方 Agent 的包必须同时具备：

- 当前版本的角色、链路、微观复现和流程审批；
- 对每个可执行判断的已审核声明式配方或受控外部执行器；
- 回放报告，包含用例数、通过数、留出用例数、结果指纹与覆盖边界；
- 单一主执行入口；首次请求只调用该入口，追问只复用结果工件，不重扫规则或大表；
- 第三方 Agent 黑盒验收记录，包括请求、调用次数、结果一致性和失败原因。

若配方不存在、仅能由 Agent 临时理解自然语言、历史回放未通过或关键问题未解决，包可以作为候选源码保存，但其状态必须是 `unverified`，不能安装、发布或被当作可完成业务需求的能力包。
